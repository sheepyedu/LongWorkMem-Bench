| 检查结果 | 冻结扣分 | 审阅判断 |
|---|---:|---|
| 当时应发 | 1.2353 | 六格包含正确时限，但另带邮箱简称和对象。单值判分过严；只接受“正确邮箱简称或全址＋正确对象＋正确时限”的敏感性复算可恢复 1.2353 分，得到 96.6471。正式分保留 95.4118。 |

### 长程记忆与盲测边界

R7 压缩请求 #70 的供应商输入为 169,027，#71 为 10,929；R12 的 #120 为 166,787，#121 为 8,263。两次均有原生 compact_boundary、供应商返回的摘要、SDK 生成的续接消息和实际下一请求的逐字绑定。R9 再次使用早期材料并正确执行；R11 也能还原四字段和早期席位。模型同时留下了名册与演算文件，因此不能把成功或错误单独归因给压缩。[压缩回执摘要](compaction.json)

原始审计遍历全部 198 份上游请求及响应、24 份原生逐轮轨迹和 277 个实际业务工具调用。逐项对齐工具签名、用户来件、模型与会话、模型提案、Claude 返回值、下一请求收到的工具反馈及真实投递记录。未匹配、未转发反馈、伪造回执号和私有评分标记均为 0。独立用相同镜像验证，宿主评分源码、答案、邮件目录和凭据文件均不可读；业务 shell 无 API Key，模拟时间拒绝未来查询。核对覆盖保存的输入及可见执行行为，无法推断模型内部动机。

### 环境、评分与校准结论

- v2 修复了 R5 可接受通讯录行范围、未登记邮箱的次日退信，以及回执工具对六月日号、06-04 和 6月4日的输入兼容性。原始 v1 的发送和确认历史按原规则复评。
- 正反例包括正确金标、空交、同义时限、工作日/自然日、重复行、列次序、重复投递、历史截止、覆盖同名文件、额外投递和错后补救。独立脚本从公开签署件、实际批次、修订与退信另算 v2 金标 100。反事实开发测试只将首批 P01 的实际占位改为 0，后续 R4 应配席位随之改变，主站和凭证保持原值。
- 对 v2 金标做单项变异：所有主站都改用末日站点 89.8931 分；所有附件席位清零 80.9212 分；每次真实投递都重复一遍 32.549 分；保留基础作业但遗漏现场附页的样例 56.2549 分；空交 0 分。这些是评分器探针，不能充当模型实测。
- 冻结评分保护了首次失误后的恢复机会，但 v2 现场相关的 50 分仍取得 49 分。大盘中许多历史资料可以合法通过目录和规则筛出；模型保留签发名册、按对象编程求解的策略有效。只加文件和字段已经产生显著成本，却没有把分数稳定拉开。下一版宜先明确**不必要的客户通知、挤占他人名额、未纠正的错误承诺**分别值多少业务损失，并在有代表性的独立案件中验证，然后冻结权重再用新作答。当前两场不足以宣称难度达标。

**格式和基础设施异常。** 坏工作簿、缺页、重复表头、重复业务键和数值单位差异均可定位。本轮审计另外发现两种异常交件（同名目录、有效 ZIP 内没有 workbook 部件）会使原解析器抛错；已补成可记录的格式失败。缺少宿主邮箱或轮末快照则按证据缺失中止复评，不产生业务零分。两份正式交付在修复前后逐项一致。可用 `python -m tasks.w4.format_review RUN` 重做 R11 的等价格式敏感性分析。[开发对照分数](controls.json)
