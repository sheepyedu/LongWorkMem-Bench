## 哪些分数反映记忆，哪些受交付口径影响

正式场合计失 14.4917 分。其中 **6.0125** 来自四份调度表的实占或最后受理号使用了开班值，另有 **4.1667** 来自回查表只列两个变动案件。这些得到的是“指定文件在指定截点是否完整”的证据；原题的“追查差别”和“交今日调度表”容易被理解为差量清单和事前计划。其余 **4.3125** 来自 R9 与 R11 的业务判断、实际分配及通知错误。没有把前两类扣分解释成记忆遗忘或补回正式成绩。

4.1 在公开材料中明确：逐案 CSV 交全十二案，调度表的实占与受理号在操作结束后填写，每轮只交当轮要求的产物。通知日期的原分值拆成两项，同日提前寄出也能单独识别。在正确解中将一封 J02 通知移到本案柜面操作前，只损失“办后才通知”一项。未改变其他业务权重。

**成本仍高。** 同模型上一版夜班首场是 98 次请求、累计输入 6.43M；本场为 123 次、10.12M，累计输入高约 57%，未缓存输入由 143,094 增到 188,853。两次工作内容和模型行为不同，无法据此孤立估算环境改动的成本效应。4.1 的默认柜面响应共用表头，并支持只查变动。按相同紧凑 JSON 编码，本场 31 次成功查询的原结果共 37,735 UTF-8 字节，共用列名后为 18,559 字节，逐项无损还原。这是响应体积离线测量，尚无新的模型端 token 实测。[4.1 同场复评、局部变异与接口对照](interface-replay.json)

宿主遍历全部原生提交、工具回传和上游请求，另按当时已经到达的邮件前缀重建全部 31 次柜面查询。均与当时模型所见相符；全部上游 HTTP 200，没有发现评分指标暴露、不明来源的回执或工具来源不一致。轮次发放前逐日验证容器来件正文与撤回路径，参评环境没有宿主日志、评分器或 API 凭据。不能从轨迹判断模型的主观动机。[审计明细与压缩回执](process-audit.json)


## 评分可复现性

固定实例 17217/A，四站各三案，共十二轮。参评工位内可读的是办理规则、原件和真实柜面回单。评分与证据归档位于宿主。对某一案发错版本会被柜面退回；窗口已发生的承运提取仍会保留。后续轮次按该场实际记录办理，无法通过改写本地台账改掉历史。

| 金标上的局部变异 | 改动结果 |
|---|---|
| 第10日只把 J01 的“兑入”改为 999 | 仅 `R10/J01/调度-兑入` 失分，扣 0.10 分 |
| 该日全表删掉“兑入”一列 | 仅该日十二案的十二个兑入项失分，共 1.20 分，其他列可单独核验 |
| 第3日按案号抢先分配，随后按真实历史正确补救 | 第3日扣 1.1083 分，随后九轮满分；全场 98.8917 |
| 多次提交同号同指令；同号异指令；用旧版本续办 | 同号重试返还原回单、实际不重复记账；冲突及旧版本均被退回 |

单条评分项权重不超过 7/12 分。四个站分别核容量，另有 1 分分成四个完整性检查，核未知客户、错误窗口、不可归案批次和台账中的未知案号。十二位客户各占约 8.2121 分。字段之间有业务依赖，不能把一千余条断言视作一千余个统计独立样本。部分案件无需主动通知，这些案件只有在实际保持安静且有正确交接记录时才获得信用。[局部变异明细](locality.json)
