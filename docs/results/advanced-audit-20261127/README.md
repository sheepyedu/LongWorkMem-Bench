## 逐题扣分与环境

### W1 · 早期未落盘会影响后续交付

种子 17217 的千问在首轮用完 4 批共享盘调用，回复中把出表列为“下一窗口”的工作；第二轮结束仍未生成关账版。第七轮又请求补发已经迁移的工牌与合同册。最终得 17.5813，其中争议预留拿到 14.67/20。时限内缺少底稿、后续取得的授权仍被正确使用，这两件事可以从同一条轨迹分别验证。DeepSeek 同种子也在第一轮窗口关闭后未交底稿，最终拿到 54.9836。每轮批数均写在用户请求里。按本批表现解读 W1 得分时，需要同时考虑批内操作安排、工作簿实现和跨轮留存。

工资簿的旧评分逻辑会在 Calc 异常退出、超时或漏产转换文件时给零。以参考工作簿模拟退出码 1，以及退出码 0 但没有转换文件，两种情况都复现了误扣。修正后要求重评原交付，并保存真实转换退出码、生成数量。对于交付物本身缺失或项目—员工名册不符的情况，可直接查到业务证据。下游简报按此前实际提交的冻结报表验算，因此早期对账不全时，后续如实转述仍可单独得分。

W1 八场都记录到原生压缩边界，共 12 次，首次均在第 5 或第 6 轮。四个种子的参考交付均得 100；两模型工资结果的平均分分别为 3.06/20、2.40/20。八场在修正后的宿主复评逐项一致，六批转换共生成 509 份工作簿，另外两场可直接从缺件或名册不符判定。压缩前后使用的是同一个工作盘，缺件与公式错误都可能拉低得分，不能仅凭压缩事件归因。

### C1 · 取件时刻比最终实现更能解释部分低分

DeepSeek 在 17217/A 的签收版为 7.20，轮末版为 98.64，合成 37.68。R5 和 R7 中依早期签发口径才会翻转的行，签收时分别命中 0/472、0/391，轮末分别达到 472/472、391/391。程序和交接信息后来都用对了。轮末余下的 1.36 分来自 archive-0 省略了空的 travel 数组，同件的 accounts、audit、totals、lots、usage 全部相符。题面写了从调拨阶段起交 travel，补一个无调拨时仍交空数组的示例，可减少这类接口分歧。

另一个真实错误出现在 17219/B。DeepSeek 将重复保证金申请再次写入处置清单，在三个截止日分别多出 19、34、43 行；题面明确要求重复 id 只办一次。评分器按整字段严格比对，建议同时列差异行数。相同种子的千问签收 9.90、轮末 100，说明同一低签收分也可能对应不同的业务正确度。正式主表保留签收与修复两列。

千问 17217/A 用完 180 次请求，完成 R1–R4，冻结了 R5 的部分交付。正式分为 14.15；R6、R7 未到达的 62 个加权项合计 57.56 分，按预算规则记零。第 180 次响应发出的 shell 命令已执行并有宿主回执。旧审计器因无下一请求而标记回传异常；修正后单列“预算结束时未回传”，继续逐项核对 CLI 与宿主日记。原分不受影响。

### S1 · 登记格式与历史版本还原可分别计量

DeepSeek 17217/A 对 80 个抽查的队次均提交 `队号 → 正确赛段名 → 四项数组`，标准解析器只接收 `队号 → 数组`。外层 JSON 解析成功，额外的赛段层被静默忽略，因此 320 个登记字段均为零。仅展开本轮同名且唯一的包装层，登记变为 26.531/30，总分由 37.812 变为 64.344，订单执行 37.812/70 完全相同。其余七场采用同一替代解析，报告逐场列出。建议在题面给一条完整的 register 单据，并在当班对不接收的形状给回执。

八场各完成 80 轮，旧公文从开幕到补办历史凭证间隔 62–78 轮。所有 640 次正式轮次的首次提交仍携带此前全部公开公文。四次重复中，DeepSeek 在已变更的订单字段对命中 807/1545，千问命中 1274/1545；历史凭证的变更字段分别命中 222/340、296/340。当前 S1 能检验跨区查找和历史版本运用，主动压缩后恢复仍需另外的配对条件。

### 如何看环境和实验范围

W1/C1 的业务工具与评分使用 Docker 工位，W1 工资簿还需宿主 Calc。S1 运行在宿主纯文本赛事引擎，模型无 shell、无浏览器、无外网工具。若要声称三类环境均验证 Docker 隔离，S1 还需要容器化复跑。本批两家模型使用同一题目的同一 Harness 配置；各题的工具权限、思考开关、阶段切换和请求上限应随成绩一起解读。
本批客户端均为 Claude Code 2.1.314。W1 办公镜像 ID 为 `sha256:0f10f159e2075cfb0932c48d39b03e22aaa2add09c459651627f61ffe6116712`，C1 为 `sha256:191083cdf6c7bda8c76158983163ead5d5cf7b77cf3033e805bb0f5296f51b4b`。各场 manifest 保存版本及镜像身份；S1 保存评分版本 2 和解析版本 3。

三题在四个正式种子上的参考解均达 100 分，S1 的空白单据对照四次均为 0 分。全部 8,024 个评分项都有可复算数值，其中 C1 预算终止后的 62 项属于未到达规则分。十二对同种子配置一致，双方实际共同到达的阶段均核对公开输入；未完场只核验到 R5。W1 八场的本地工资簿和 C1 八场的两套交付重放均逐项一致；S1 八场均从原始回答还原至已存单据和成绩。

宿主记录 2,140 次上游请求尝试。2,126 次有用量，已知输入 124,226,284 token（其中缓存读取 117,699,712），输出 4,274,343 token。14 次超时缺用量，故 token 数是观测下限。另有 16 次上游已返回 200、适配器交付 502，其中 14 次工具 JSON 随输出截断、2 次工具参数 JSON 不完整或不合法。它们有上游回执和用量，已计入消耗。单场 50–180 次请求、观测累计输入约 1.01–13.82 M，尚未覆盖立项提出的单题 1k–2k 请求规模。

W1/C1 的工具回执中出现过 37 次输出截断标识，W1 出现 20 次 ERP 窗口关闭标识。对过窗和命令报错分别保留证据。C1 两场的历史请求命中 `guarantee.rerun` 标记，逐条定位到模型自己命名的复跑文件及该消息的历史重放；未发现由宿主下发隐藏评分内容。C1 预算末次已执行、无法再回传的工具另记 1 次。校正后的八场会话、参数与执行日记对账均通过。

## 如何复核

每场私有归档位于实验机的 `rollout/<题号>/<批次>/<模型>-<种子>-<版本>/`。其中 `trajectory.tar.gz` 含原始输入输出和运行证据，`files.json` 列出成员哈希，`SHA256SUMS` 校验整个压缩包。逐场的《审阅.md》附各阶段得失、操作摘要、原子评分 CSV 和原始证据位置。公开 runs.csv 包含归档哈希，可与本地文件交叉核验。

- W1 从冻结目录运行 `python -m w1.advanced RUN --details`，对账使用 `python -m w1.review RUN`。
- C1 运行 `python -m c1.settlement_grade RUN --backend docker` 与 `python -m c1.review RUN`。评分 Docker 需能读写临时副本。
- S1 运行 `python -m s1.circuit_review RUN`。同赛段包装层的诊断使用 `python -m s1.circuit_registration_audit RUN`，其替代分单列。
