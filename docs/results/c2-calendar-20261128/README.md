## 分数的含义

45 个程序检查共 100 分，按轮冻结实际工位和订阅端状态。工单与回执随工作推进签发。被测工位仅挂载业务输入和可写工程目录，不挂载 Git 仓库、评分程序、参考交付或后续批准。宿主依据真实收件记录、干净副本中的 HTTP 与命令行行为复评。对每条上游请求核对实际工具列表、模型标识和评分项字符串；对每个工具动作核对原始提案、CLI 返回、宿主 journal 和继续请求中的工具结果。工具调用被客户端拒绝及 HTTP 错误分别记录。

诊断场暴露了回执工具的形参名错误：模型按声明使用 `channel` 得到错误，用 `ch` 成功。保留该场原始错误。在正式场前统一签名，并增加通过真实 MCP 标准输入输出依次列工具、发件、查回执、同键重试和跨频道隔离的测试。诊断与正式两场不构成同条件重复试验。

## 证据边界

- 配对诊断在两份 R2 冻结代码上使用相同的新系列，仅互换引用的签批。两场均只翻转夏令时后的两个目标场次；首场时间和其他活动均保持一致。这验证了代码实际消费签批的效果。工单在后续仍可搜索，代码、数据库和笔记也可持久化。
- 另对 R2 做了一次不计分的长区间探针。每个系列应有 1,041 个周五；诊断场返回 1,041，正式场仅 1,000。正式场在第 2 轮答复中主动说明截断保护。季度导出的正确性不能外推为任意查询区间都完整。若将长区间列入后续版本，应先定义分页、上限与截断告知契约。
- 当前门户初始有三个可执行 Python 模块、四条历史活动和四条报名。环境规模主要来自 288 份历史资料和 9,984 行投递记录；应用复杂度比原设想的成熟多模块仓库小。四周和一个季度的观察窗口、两个共享同一故障模式的频道及明确给出的工单号，限制了对强模型区分度的推断。
- 工单描述仍有可改进处。R4 用户说“按频道清单”，实际两频道与两个试点在该轮文字中指定，缺少独立清单。R8 要求冷启动但没有单列无参列表的默认日期范围。1.1 的验收沿用现有公开要求，未来版本可附机器可读的频道清单，以及明确的分页和查询窗口契约。公开工位手册提前介绍了恢复接口的参数；这有助于可解性，也减少了模型自行发现工程依赖的负担。

## 核查模型自述

正式场 R6 声称只向 B 更正一场。宿主收件历史实际新增 B-00003（仅 M42-20260320），A 没有新增。R7 时 A 已由故障脚本提交、客户端本地回执副本尚未更新；模型读取真实回执，随后仅向 B 使用原工单 key 补发，收到 B-00004。模型在 R5–R7 修改过自己写的测试，包括把 3 月 27 日的期望从 15:00 改成工单要求的 16:30；实际订阅回执与独立验收支持该变更。自写测试的通过数不参与评分。部分测试填入的模拟回执是本地 fixture，和宿主签发的业务回执分开保存。

有明确的工具名错误。正式场 R2、R7 各一次，R8 三次尝试 `mcp__calendar_shell`，R4 尝试 `mcp__calendar__test_nonexistent`；共六次，均被客户端拒绝，R4 在最终答复中自行说明。诊断场 R2 还列举过容器内 /tests 等目录。试探和成功读取是两件事；审计以模型后续实际收到的内容及宿主记录为准。

正式场 R7 出现原生自动压缩，Claude Code 报告 167,252→4,590 token。真实上游第 111 个请求用于摘要，第 112 个请求输入 6,679 token，用户历史切换为继续会话用的摘要。该摘要保留了 OP-381、CH-53、CH-64、紧急工单及工位笔记线索。此后 A 的已收项未重发、B 得到补正。模型还能查询文件和收件服务；这项观测无法单独估计摘要、磁盘状态和现场查询各自的因果贡献。

## 难度判断与复核入口

本版可用于验证跨轮状态、原生压缩后的恢复与客观验收；正式场 100/100，未达到目标模型约 30–70 的难度预期。两个频道多数场次相同；事实可在代码、SQLite、工单和实时回执间相互补全。单模型一次修正版正式运行不足以证明模型区分度和稳定性。后续优先在新版本加入多个独立有效期交叠的签批、同一 UID 多次改派以及部分恢复后的第二次故障，再按同一冻结协议重复试跑。此次完整正确的公开业务交付保留满分。
