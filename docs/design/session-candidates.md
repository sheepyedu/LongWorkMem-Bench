# LongWorkMem-Bench｜三类九题：基准调研与设计讨论稿

2026 年 11 月 26 日 · 供选题讨论。九道题均为拟制任务，本轮完成资料与样本调查，尚未制作题包或运行模型。

**我建议先验证一种能力：同一句“继续处理”，模型能否根据先前亲自看到的事实，做出不同且正确的动作。** 在 Work 里，这可能改变一封邮件的收件人；在 Code 里，可能改变重放旧数据时采用的版本；在 Simulation 里，可能改变岔口的路线。下面先给出研究依据，再给出九题和环境方案。

## 二、我的选题思路

Work 按业务结果验收，操作已有网站也归 Work。Code 交付可运行的软件，开发网站归 Code。Simulation 交付环境中的行动结果，统一提供文本观察和合法动作。**用什么工具与属于哪一类是两个问题**：用 Python 做账仍可归 Work，用 Python 修改对账引擎才归 Code。

每题准备一对共享背景的版本，**只翻转一条早先已公开且仍有效的信息**。结束请求相同，至少一个可观察结果必须随之改变。允许代理做笔记、建索引、重读开放资料；能高效找回证据同样是成功。每题的满分暂定 100 分，下列五项为程序检查点的设计权重；正式题面还需公开字段语义、时间边界、容差及并列处理规则。

### Work｜业务交付

#### W1　跨月采购关账、项目结算与奖金分配

- **准备环境**：两个月的订单行、分批入库、退货、发票、项目审批及人员工时；沙箱提供 CSV、可重算的 Excel、归档目录和本地邮箱。出题人从一张事件表生成各来源数据，另写独立参考账验证口径。
- **交互（拟 10 轮）**：第 1–2 轮建逐行对账底表；第 3–4 轮冻结月末报表，转去写异常简报；第 5–6 轮收到次月补件和部分项目放行通知；第 7–8 轮用已结项目奖金池按工时分配并处理一次有生效期的转岗；第 9–10 轮归档并向财务、项目负责人分别投递。
- **决定性依赖**：保留前案 PO-217。订 100、收 95、退 5、发票 100，月末净入库 90；次月补 10 后当前净入库 100。配对版本只改员工转岗生效月份，两份关账快照和总奖金均相同，员工明细必须不同。
- **100 分检查点**：按稳定行号关联及去重 15；已关账异常集合与会议口径 20；补件后的当前状态与旧快照同时正确 20；奖金和尾差逐人正确 25；工作簿改值重算、附件范围和实际投递记录 20。

#### W2　招标澄清、版本修订与分供应商发信

- **准备环境**：为多个标包生成招标正文、带签署页的补遗、讨论稿、问答邮件、供应商授权矩阵。可搜索 PDF、DOCX 和邮件；每条条款有稳定编号、适用标包和生效日期。所有收件地址均指向沙箱。
- **交互（拟 11 轮）**：先建条款与证据索引，登记不同文件中相互冲突的交付日；再为会议做待确认清单。中途加入一份签署补遗和一份更新但未签的草案。返回主线时，用户只说“按会上确认的范围出稿”；最后撤回一个标包的对外发送许可，要求其内部档案仍完整。
- **决定性依赖**：只改变早期闭门会议批准给某供应商的标包。两个版本都收到同一条“按最终名单发送”，但该供应商的附件、正文条款或投递资格应随授权改变。这样能检验读懂材料后是否在实际发信时正确使用。
- **100 分检查点**：证据索引逐条可定位 15；签署状态、日期及版本覆盖关系 25；未决事项和内部完整档案 15；每个收件人实际取得的条款与附件集合 30；批准前零发送、回执和唯一投递 15。

#### W3　批量售后、缺货替代与预留到期

- **准备环境**：文本化零售门户、用户邮箱、库存预留和发货事件表。预置同款不同规格、分批订单及稳定 SKU；业务时钟按轮推进。用户答复由固定脚本提供，两种策略在相同状态下得到相同答复。
- **交互（拟 9 轮）**：受理多笔退换请求并确认每位客户的替代偏好；首轮预留现货、草拟处理方案；插入独立物流工单；返回时首轮预留已到期且一款缺货；用户要求“按各自原先的选择办”。随后核对发货单、退回的额度与剩余待办。
- **决定性依赖**：一位客户是否接受无背光替代键盘。固定末轮库存、价格与请求，让同一订单在两个版本中分别“换键盘并换温控器”或“只换温控器”。同时检查其他客户是否被串单。
- **100 分检查点**：订单及许可对应正确 15；首轮预留与草稿 15；过期处理和库存守恒 20；最终退换集合逐商品匹配 30；唯一发货、退款和待办对平 20。

### Code｜持续软件开发

#### C1　多来源工单事件库的连续升级

- **准备环境**：小型 Python CLI、SQLite 存量库、旧 CSV、新 JSONL、可重复的乱序及冲突事件。私有测试器能在分片写入中触发进程退出，并从空卷重新建库。
- **交互（拟 12 轮）**：保留旧入口并迁移前导零编号 → 接入第二来源并确定同版本冲突口径 → 处理乱序与重复 → 第 17 片写到一半时中断 → 临时提取独立日志的失败 ID → 接续导入 → 加入撤销与历史查询 → 从初始库完整重放。阶段间沿用代理的提交和数据库。
- **决定性依赖**：配对改变早期冲突处理规则：普通同版本冲突一律隔离，或允许带指定审批标识的更正覆盖。同一条获批更正的现态、审计记录和历史报表相应改变。输入有稳定事件 ID 与入站序号，参考重放明确定义处理顺序。
- **100 分检查点**：旧入口和无损迁移 15；版本回放与冲突 20；中断恢复、独立日志及唯一提交 20；撤销和历史查询 20；干净重放、报表及旧功能回归 25。

#### C2　跨时区排期门户与日历导出

- **准备环境**：可运行的小型 Web 应用、虚拟时钟、固定时区数据库、SQLite、浏览器文本 DOM 和 ICS 解析器。准备跨夏令时的活动，选用当地上午 10 点，先排除切换小时本身的歧义。
- **交互（拟 10 轮）**：修复跨日显示并保留接受 UTC 的旧 API → 新增重复活动，用户指定“固定场馆当地钟点” → 临时撰写邀请文案 → 加入单次改期及取消 → 实现移动/桌面共用的深链 → 生成下一季度日历与变更通知。冻结后重建网站，用浏览器、API、ICS 三个入口核对。
- **决定性依赖**：早先约定固定纽约当地上午 10 点，或固定首次活动的 UTC 时刻。切换夏令时前两者输出相同，切换后相差一小时；末轮只要求“导出下季度全部活动”。改单场必须保留同系列其余场次与事件身份。
- **100 分检查点**：数据迁移和旧 API 15；跨时区递推与边界日期 25；单次例外及稳定事件 ID 20；深链、界面、ICS 与库状态一致 25；重复导出及旧行为回归 15。

#### C3　带迟到修订的需求预测与历史重放

- **准备环境**：离线销售、促销、退货数据，每条同时记录业务日期和首次可知时间。锁定 pandas、scikit-learn、固定种子与单线程基线，单次参考训练拟控制在 2 vCPU、2 GiB、90 秒以内。用纯 CPU 的小模型和合成时间序列校准。
- **交互（拟 10 轮）**：实现按发布日期取数 → 做滚动回测，锁定特征口径 → 生成一页模型交接记录 → 注入次月才收到的促销修订 → 对历史两个发布日期和最新一期分别生成预测 → 交付可复跑命令、预测表和误差分解。
- **决定性依赖**：一项促销在签署日可用于预测，或须等到公开发布日期。把预测截止时点放在两者之间，可直接核验相关特征。隐藏测试还改变未来标签，检查过去特征和预测是否意外改变。新旧版本允许不同合法模型，用其提交的冻结模型独立重算输出。
- **100 分检查点**：按当时可知信息构建特征及无泄漏 30；时间切分与误差指标重算 20；历史发布可复现 20；迟到订正的影响范围 20；离线 CPU 重跑 10。先测朴素季节基线，正式发题前冻结公开最低精度门槛，防止常量预测混过流程检查。

### Simulation｜交互模拟

下列三题分别考**更新规则、维护空间状态、追踪物体身份与处理过程**。模型看到局部文本观察、合法动作和可见事件，可在工作区做笔记。模拟器私有状态、解题器及评分器放在独立进程。允许多种合法策略，通过实际结果验收。

#### S1　跨幕卡牌构筑与临时赛制修订

- **准备环境**：自建小型文本牌组引擎，包含牌型、商店、消耗牌、持续加成、分幕目标和确定性结算。用原创牌面与公开规则，预生成牌堆、商店与事件序列。用有限搜索核验每个种子至少有两条可行构筑。
- **交互（拟 9 个任务轮）**：第一幕侦察获知终局会压制哪类加成 → 两幕比赛积累资金，保留或卖出关键牌 → 支线赛临时翻转一种计分规则 → 支线结束恢复常规规则 → 回到商店，在有限资金下选终局组合 → 执行终局并结算。每个任务轮容纳多个出牌或购买动作。
- **决定性依赖**：配对中保持后期手牌、商品、资金和后续牌序相同，只改早先公布的终局禁法。两件等价位组件分别增益对子、同花；生成器须证明至少有两个合法解，同时两版本达标选择的集合互不重合，避免总能买同一张。自然长会话另按实际自有牌组评分。
- **100 分检查点**：前两幕真实目标 15；临时赛制下结算达标 15；规则失效后正确恢复 15；冻结商店的跨版本构筑能达终局门槛 30；多种子自然终局与资源结余 25。所有可达标构筑等价得分。

#### S2　局部可见的仓储迷宫与大件回运

- **准备环境**：CPU 网格世界，文本返回相邻通道、地标、载荷和当前可行动作。地图有窄门、单向通道、钥匙柜和有限电量。生成器在“位置、载荷、钥匙、通行状态”的联合状态上搜索并保存可行成本界。
- **交互（拟 10 个任务轮）**：轻载勘察并领取钥匙 → 读到只公布一次的跨区通行通知 → 小件委托短暂改变目的地 → 回主线取宽件 → 在外观相同的中转岔口选支路 → 装卸并返回指定货位。等量轮数下可通过支路数量、通知到使用点的间隔调难度。
- **决定性依赖**：配对只变更远端哪个门完成了拓宽。在岔口处使用相同局部观察、载荷、电量和移动预算，两条本地动作都合法。用解题器证明两版本分别存在可行路线，且剩余预算下错误分支不能靠试遍两边补救。
- **100 分检查点**：勘察委托及钥匙状态 15；支线小件送达 15；恢复主线时货物和资源正确 15；配对岔口与远端合法通行 30；最终送达并满足步数、电量限制 25。普通导航短题用于诊断动作接口。

#### S3　多批次器材整备、借出与召回

- **准备环境**：原创建模的纯文本具身环境，借鉴 ALFWorld 的容器、物体与状态谓词。相同型号的器材有不同序列号和批次，托盘可移动；只有在检查台扫描才能看见批次。虚拟时钟驱动清洁、干燥和交付时窗，每个种子用专家规划器验证可行性。
- **交互（拟 11 个任务轮）**：接单并拆箱扫描 → 按公开工艺清洁、干燥两批器材 → 临时借出指定件给另一工位 → 接收其归还物和更正记录 → 执行先前公布的批次召回约定 → 重新配齐剩余订单，封箱交付。模型必须持续追踪“哪件东西，经过什么处理，现在在哪个容器”。
- **决定性依赖**：早期质量通告指定要隔离的批次。末轮托盘外观、当前位置和交付指令相同，正确封箱成员不同。重新扫描允许但消耗公开的搬运时间；分别记录依靠先前笔记和付出代价重新确认的成功路径。最短可行解验证时间窗合理。
- **100 分检查点**：接单与处理工序按对象匹配 20；临时借还的身份及位置正确 15；召回目标全部隔离且正常件未误收 30；封箱成员、数量与工序状态正确 25；时窗内完成 10。评分端读取动作前后状态，口头报告不触发分数。

## 三、环境怎么准备，交互怎么控制

| 层 | 制题时准备 | 运行与取证 |
|---|---|---|
| 业务与代码环境 | 锁定 Docker 镜像、依赖、时区与虚拟时钟；Work 共用文件、邮箱、业务数据库，Code 每题带基础提交、旧版本数据、构建与回归入口。 | 每个策略从同一初态创建独立卷，单次会话中工作区持续存在。网页用文本化 DOM。邮件投递到内部收件箱。首次返回主线与最终交付都冻结。 |
| 模拟环境 | 定义观察、动作、转移及终止协议；公开示例和廉价重置接口用于作者调试。为随机结果按事件生成种子，给开发题配参考策略与必失败变体。 | 被测会话只能调用当前观察与合法动作，不能读私有存档或自行回滚。控制器保存观察、动作、世界前后状态与资源账，可逐步确定性回放。 |
| 会话导演 | 每题写逐轮公开请求、材料释放点、可回答的澄清问题、持久约定、改版与失效事件；标记相关、半相关、无关和自然转段。 | 同策略配对用同一脚本。新轮按业务事件或预设轮界释放，阶段未达标也保留真实快照和后续补救机会。自然轨迹与注入正确前置状态的诊断轨迹分别计。 |
| 独立评分 | 从原始事件生成合法解；第二人仅凭公开规则独立重算；准备等价正确解、只错一个业务关系的错误解。 | 评分器读冻结副本；校验新增能力、旧约束与不可撤回事件。记录评分脚本、输入、快照摘要、基础设施失败与缺失项。 |

**规模预算怎么理解。** 九张卡中的 9–12 轮是用户提出阶段目标或接收业务事件的轮次。首版长题继续以每题约 **1,000–2,000 次模型请求、几十 M 至几百 M 累计输入**作为规划尺度；每题实际预算由参考轨迹和开发试跑校准。举例，用 1,200 次请求、平均输入 60k 估算，累计是 72M，峰值仍应从逐请求日志读取。这里估算的是数量级。一次本地动作、一次工具调用、一次上游模型请求分别计数。小样若只需很少请求就能完全解决，保留其诊断价值，正式长题另增加真实分支、对象、版本或并行待办。刻意拆碎动作、重复输出日志会损害评测。

**每个家族都做三条同存档诊断。** 选一个关键决策点，将后续状态、动作预算与随机事件固定。① 只给此刻可见信息；② 额外给历史中当时已经公开且仍有效的事实；③ 从头运行完整会话，允许工作文件、检索及自主整理。前两条评估局部难度，第三条评估端到端能力。实际代理自产状态可能和标准存档不同，另在它自己的快照上分叉短对照，避免把上游失败都归因于遗忘。配对变体在多种子上随机顺序运行，防止猜同一动作总能得分。

**哪些结果值得扩题。** 若①就稳定通过，先排查末轮提示、文件名、可选动作等是否泄漏答案；若②也普遍失败，先查规则歧义、搜索难度、训练耗时或评分器；若②可解且两种历史要求不同交付，就具备测试上下文使用的条件。正式对照在相同模型、Harness、业务工具和预算下比较原生与 CLM，记录“提议编辑 → 框架接受 → 实际后续请求消费 → 到期交付”，另记原生压缩、请求数、缓存、输出和时间。策略平局也应保留。首轮不以排行榜、胜负或删了多少 token 决定留题。

## 四、希望一起确定的方案

**我建议九题先作为候选库，首批只实现 W1、C2、S2。** W1 有已知数值和关账边界，容易先检验评分器；C2 的两套时间约定在夏令时前给出相同表现，之后才出现可观察的一小时差，特别适合测规则是否跨阶段延续；S2 的正确方向和最短成本能由求解器验证，最容易把历史依赖与游戏水平分开。若更重视继续已有代码样题，C1 可以替换 C2；若研究重点是卡牌资源取舍，S1 可优先，但需要先验证场景不存在通用构筑或不可控运气。

**待确定的三项选择**：首批是否选 W1/C2/S2；Simulation 首轮是否同时设计 S1 的配对商店但暂缓完整战役；成本校准是否先以短对照和自然试跑定上下限，再锁正式预算。选定后制作输入材料、Docker 环境、私有评分器和三组诊断存档。
