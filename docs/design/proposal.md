# LongWorkMem-Bench｜面向工作场景与交互模拟的长程记忆评测基准

本文据项目已讨论的立项目标、样题与三类任务方案整理，供公开协作。基准处于设计阶段，文中的运行规模、预算和评分为拟议安排，待环境落地后用试跑校准。

## 研究问题

一笔订单在月末结账时缺货，次月已经补齐。智能体需要更新今天的可结算金额，同时保住昨天报给财务的数字。这样的工作要求模型判断**哪条信息仍有效、哪项决定曾被取代，以及后续交付应使用哪个时点的状态**。

本项目拟在负责工具调用、会话状态和原生压缩的运行框架（Harness）中，考察模型经历多轮执行、任务切换和上下文整理后，能否接续已有成果。评测同时关注最终产物、阶段进展、关键依赖的正确使用，以及达成这些结果的请求和计算成本。

## 数据集与交互

首版约 50 条完整会话。每条按**主要交付**归入一个领域。工作量、领域比例和长短档位依据试跑确定。

| Domain | 任务范围与验收依据 |
|---|---|
| **Work** | 文档、邮件、表格、数据分析及操作现有业务网站。验收报表、收件箱和业务系统中的实际结果。 |
| **Code** | 开发或修改软件，包括 Web 开发、自动化和轻量机器学习。验收可运行代码、隐藏测试和旧功能回归。 |
| **Simulation** | 在策略游戏或具身模拟中执行多阶段任务。以文本返回局部观察、合法动作和反馈，验收真实动作后果及环境终态。 |

用后续阶段真正需要的文件、决定和待办连接各轮。条件和外部事件逐轮发布，三类任务均允许模型做笔记、维护索引、按业务权限重读证据。

| 任务关系 | 例子 |
|---|---|
| **相关** | 核对采购明细后编制部门报表，沿用同一套金额口径。 |
| **半相关** | 暂停编表，基于已有明细为会议整理简报，区分已确认与待核金额。 |
| **不相关** | 短暂转去处理另一服务的失败日志，随后回到原任务继续。 |
| **任务转变** | 完成财务结算后，用核定金额与获批工时进入奖金分配阶段。 |

## 规模与评测

| 项目 | 初步安排 |
|---|---|
| **会话长度** | 每题几轮到十几轮用户交互。一个用户轮可包含多次模型调用、工具操作与结果核查。 |
| **请求与输入量** | 长题预计每题约 **1,000–2,000 次模型请求**，累计输入为**几十 M 至几百 M token**。累计输入含每次重发的历史；单次请求峰值、缓存命中和未命中另计。 |
| **环境** | 在 Docker 沙箱内运行办公工具、本地邮件及业务服务、代码仓库或模拟器。纯文本模型可通过文件、文本化页面、命令行或动作接口参与。 |
| **评分** | 用检查点冻结阶段产物与环境状态，程序逐项核对。报告最终完成率、阶段分、恢复情况和关键依赖延续率。 |
| **策略比较** | 同一模型、工具和预算下比较原生方案与可编辑活跃上下文的 CLM 方案。分别记工具可用、编辑被接受、编辑进入后续模型请求、原生压缩及真实成本，再另表比较不同模型或 Harness。 |

### Simulation 如何测出历史信息的价值

**同一个决策点，给出相同的当前观察，只翻转一条早先已知的信息。** 在跨关卡牌构筑题里，早期侦察揭示终局禁用哪类加成。经过数幕比赛和临时赛制后，智能体在资金、手牌和商品均相同的商店中需要选择与终局兼容的构筑。在局部可见的仓储迷宫中，早先的拓宽通知决定哪条远端通道能运送大件，即使当前岔口看起来完全一样。

出题时用求解器确认两种历史各有合法解，并验证预算内能否靠同一个动作蒙混通过。关键存档设置“只看当前观察”“补上此前已公开且仍有效的事实”两种短对照，再考察完整长会话。若只看当前就稳定成功，应增强历史依赖；若补齐历史仍普遍失败，先降低搜索或规则推理难度。观察、动作和随机事件按种子回放，阶段达标、动作成本和上下文管理开销分别报告。

## 两道候选样题

### A｜跨月采购对账、项目结算与奖金分配（Work）

借鉴 [WorkBuddy Bench](https://github.com/Tencent/workbuddy-bench) 的多材料制品验证方式。提供两个账期、三个项目的订单、分批入库记录、退货单、发票、审批邮件与人员分配表。以订单 **PO-217** 贯穿全题：订购 100 件、单价 100 元，当月入库 60 件与 35 件，退回 5 件，发票按 100 件开具。月末净入库为 **90 件**，数量差 10 件、金额差 1,000 元；次月补收 10 件后当前状态发生变化。

| 检查点 | 用户交互与任务推进 | 程序验收与分值 |
|---|---|---|
| CP1 建立底表 | 第 1–2 轮，按采购行号串联订单、入库、退货和发票，处理一行订单多次入库、重复流水与孤立记录。 | 订单行关联正确 **10**；去重及孤立记录集合正确 **5**。 |
| CP2 对账与汇报 | 第 3–4 轮，生成数量与金额两张异常表，同一订单行可同时出现。临时编写会议简报，分别给出异常订单行数和各类异常数。 | 净入库及数量异常集合正确 **10**；金额差正确 **5**；简报的订单行计数正确去重 **5**。 |
| CP3 跨月补件 | 第 5–6 轮，补收入库单到达。恢复原工作簿，只解除审批邮件所列项目的暂缓，冻结上月报送结果。 | 上月仍为 90 件、差额 1,000 元 **5**；当前为 100 件且对应异常关闭 **10**；放行范围正确 **5**。 |
| CP4 分配奖金 | 第 7–8 轮，按审批表奖金池和核准工时分配到分；尾差给工时最高者，并列时给员工号较小者。随后只对指定月份、项目修订人员归属。 | 奖金池与可分配项目 **10**；员工金额、舍入及尾差 **10**；归属修订范围 **5**。 |
| CP5 归档投递 | 第 9–10 轮，归档可重算工作簿。沙箱财务邮箱接收完整奖金表，各项目负责人仅接收本项目汇总，回执写回索引。 | 改一位员工工时后分配联动且总额守恒 **10**；实收名单、附件和次数正确 **5**；回执与文件匹配 **5**。 |

**合计：10 个用户轮次，5 个检查点，100 分。**

### B｜多来源工单事件库的连续演进（Code）

借鉴 [SWE-Milestone](https://arxiv.org/html/2603.13428v4) 的持续演进方式。智能体在同一代码库和数据库中，把旧 CSV 导入器扩展为可接受 JSONL、重放事件和查询历史的工具。环境使用 Python、SQLite 和 CPU。贯穿实体 **A/0017** 的版本 1 为待处理、版本 3 关闭、版本 2 晚到、版本 4 撤销。当前报表应排除已撤销工单，截止版本 3 的报表仍显示“已关闭”，来源 B 的同号工单独立。

| 检查点 | 用户交互与任务推进 | 程序验收与分值 |
|---|---|---|
| CP1 存量迁移 | 第 1–2 轮，保留旧导入命令，按映射表恢复带前导零的历史编号，将无法唯一还原的行单独导出待核。 | 旧命令及格式回归 **5**；已知编号恢复正确、歧义行完整隔离 **10**。 |
| CP2 事件回放 | 第 3–4 轮接入 JSONL，按来源和原始编号识别实体、按业务版本更新。同版本内容冲突时保留原状态并登记，再投放乱序与重复批次。 | 实体身份正确 **5**；乱序及重复输入的当前状态正确 **10**；冲突登记与受影响状态正确 **5**。 |
| CP3 中断与切回 | 第 5–8 轮，控制器在第 17 片部分写入、事务提交前中断进程。用户临时要求从另一份日志提取失败 ID，随后只要求“继续刚才的导入”。 | 半写分片未提交 **5**；失败 ID 集合正确 **5**；续跑无漏写、重复业务或重复审计记录 **10**。 |
| CP4 撤销与历史查询 | 第 9–10 轮加入撤销事件，同时支持按截止版本查历史。沿用早先确定的实体键、冲突规则和旧入口。 | 撤销范围正确 **5**；截止版本 3 与 4 的查询均正确 **10**；旧格式与冲突规则回归 **5**。 |
| CP5 全链复验 | 第 11–12 轮交付当前部门汇总和月末历史明细。评分器从初始库重放，并在隐藏用例里打乱无冲突事件、插入重复批次。 | 两套报表逐实体正确 **10**；完整重放与中断续跑的数据库状态一致 **10**；旧入口通过原始夹具 **5**。 |

**合计：12 个用户轮次，5 个检查点，100 分。** 上述两题为讨论用的候选设计；题包、参考解、评分器和跨策略真实运行需在试跑阶段验证。
