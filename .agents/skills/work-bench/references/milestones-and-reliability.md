| 基准与核查对象 | 难点从哪里来，原方法怎样评分 | 可移植的做法及边界 |
|---|---|---|
| SWE-Milestone，Navidrome v0.57.0→v0.58.0 | 真实演进区间聚合为里程碑 DAG。多媒体库的持久化层 → 核心服务与扫描器 → API → UI 是数据中三条有理由的边。连续模式沿用代理的代码；独立模式从规范快照起步。 | 让多个晚期功能依赖此前产物，并保留干净起点短对照。DAG 深度与成绩负相关属于论文中的观察；复杂度须由功能与回归检查体现。 [样例依赖表](https://huggingface.co/datasets/DeepCommit-ai/SWE-Milestone-data/blob/main/navidrome_navidrome_v0.57.0_v0.58.0/dependencies.csv) · [论文 §4–5](https://arxiv.org/html/2603.13428v4) |

| τ-bench | 同时满足用户意图、领域政策和工具依赖。评测实现重放参考操作，比对数据库状态，对指定回答内容另行核查；论文用 pass^k 描述多次运行全部成功的可靠性。 | 用真实后态检查交付；允许等价路径。总分之外给关键业务的重复成功率；记录模拟用户变化，LongWorkMem 的固定脚本可减少这一波动来源。 [论文](https://arxiv.org/abs/2406.12045) · [上游评分实现](https://github.com/sierra-research/tau-bench/blob/main/tau_bench/envs/base.py) |
| CTXAgent | 在长会话按距离建立事实、短暂观察和持续指令，使用确定性探针；论文还区分跨过压缩的探针。 | 用授权生效期、原始签收记录替代任意口令，让旧事实在后续业务交付中产生可验差异。保留文件检索和外部记忆作为有效策略，区分原生压缩日志与按 token 下降推测的压缩。 [论文 §3.3](https://arxiv.org/html/2610.34425v1#S3.SS3) |

### SWE-Milestone 的分数值得借鉴在哪里

按论文 §5.1，设里程碑要求修好的测试数为 R，实际修好 F 个，本应继续通过却被破坏 B 个。Recall = F/R；Precision = (F+1)/(F+B+1)；两者的调和平均为里程碑分。先在演进区间内平均，再在区间之间宏平均。另报完全解决率。例：R=4、F=3、B=1 时，Recall=0.75、Precision=0.8、里程碑分约 0.774。躺着通过大量旧测试不会冲高 Recall。官方实现的 resolved 判定还检查应有的 P2P 测试是否缺失，并处理 NONE_TO_PASS 分类；复现时应固定版本。 [论文公式 1–4](https://arxiv.org/html/2603.13428v4#S5.SS1) · [冻结版本的 evaluator](https://github.com/DeepCommit-ai/SWE-Milestone/blob/17a8f1593e172e26b36cea15e2b30fb9536c93f5/harness/e2e/evaluator.py)

本项目建议按业务影响定权，分别报告新增、保留、修复，再合成总分。某期只有维护职责、没有新增要求时，应为该职责定义可观测的验收样例；不要硬套 R=0 的公式。

### 用仓库自己的失败验证迁移是否有效

C2 正式场 184 次上游请求、169 次实际工具动作，跨一次原生压缩后 45 项全过；修复评分后，空操作从 16.0588 分降至 3 分，正确作答仍是 100。清理被动得分解决了评分有效性，对这份强模型作答的天花板没有影响。诊断场和正式场有不同的工具接口，两场 100 不能证明同模型重复方差为零。[C2 审计及对照](../../../../docs/results/c2-calendar-20261128/)

S1 中旧格式解析曾漏算可唯一解释的登记；C1 的提前取件和试跑中断也改变过成绩含义。先统一口径，再讨论真实业务差距。[24 场审计](../../../../docs/results/advanced-audit-20261127/)
