## 售后服务手册分批发布与历史勘误

六家客户、两个系列、一个十二轮连续的 Claude Code 会话。期初共享盘有 628 份只读文件，随后逐日投递来件。两类正式产物为手册和交接工作簿。业务时钟独立于推理耗时。实例代号 17217/A 固定；模拟邮箱仅接受 office.test。生成器分发的是签署材料、营业规则和用户委托。评分程序、标准答案、参考测试、快照和日志位于工位外。出题人与评分工程师可阅读本目录，参评进程只挂载工位。

| 日 | 工作或插单 | 冻结证据与分值 |
|---:|---|---|
| 1 | 接手旧版和四笔未结案 | 12 个在用版号 3，旧件状态与行动 2 |
| 2 | 六月评审，暂缓发件 | 三项提案 2，草稿对象及数量 2，冻结内容 2 |
| 3 | 首批发布 | 收件人与动作范围 6，首批附件 7 |
| 4 | 查回执，办理退信和固定旧件 | 首批12案截点 4，补办对象 3、附件 3 |
| 5 | 通讯录局部变更 | 两个客户的三类职责 3 |
| 6 | 新网点补发 | 对象 5，沿用有效条款 6 |
| 7 | 收未来生效的验收函 | 日期及行动 4 |
| 8 | 暂转设施值班 | 两席最后签署的调班 2 |
| 9 | 切回主线，生效日前办理 | 当日对象 4、附件 5 |
| 10 | 差量发布 | 应变对象及多发 6、附件 8 |
| 11 | 历史审计与勘误 | 旧批准 3、实际附件 4、截至第4日确认数 3、现行义务 3、纠正对象与附件各 2 |
| 12 | 期末交割 | 11 案的状态、动作和负责人 6 |

每组按明确对象/字段给部分分。多发、重复主题及错误操作保留在证据中，只有草稿的客户仍属未发。静默轮的额外邮件最多扣该轮 1 分，最低零分。截止日查询使用宿主保管的原始邮件，确认按业务时钟生成，改写本地文件不能改动旧附件。历史恢复组按首批真实投递决定补救名单，并包含共同的固定旧件。未曾正确履约的首发即使后来追回也保留原处置分。延迟保持率从 R3→R6 的四对案件另行统计，给出首次成功分母。

## 运行与复评

需要 Python 3.12、openpyxl、Docker；正式运行还需要 Claude Code 可执行文件和宿主环境变量 `ARK_API_KEY`。正式命令创建新的空运行目录。独立 VM 需使运行目录在宿主和 VM 上同路径可写。

```sh
docker build -f tasks/w1/Office.Dockerfile -t longworkmem-office:1 .
docker build -f tasks/w4/Release.Dockerfile -t longworkmem-release:1 tasks/w4
mkdir -p runs
W4_TEST_ROOT="$PWD/runs" python -m unittest discover -s tasks/w4/tests -t . -v
python -m tasks.w4.pilot runs/w4/example
python -m tasks.w4.pilot runs/w4/example --replay
python -m tasks.w4.audit runs/w4/example
```

运行器记录实际镜像 ID、CLI 与 git 版本、时间、业务回执、原生会话和每次上游请求。默认使用火山方舟 DeepSeek V4.1 Flash 1017 的供应商默认推理配置；无测试请求上限。离线复评仅读取冻结产物和邮件；传输与声明审计还需要本地原始轨迹。分轮得分、技术缺口与实测条件见仓库实测索引。

## 现场服务附页版

复现现场附页版使用 `--edition 2`，重现基础版使用 `--edition 1`。复评依 manifest 选择冻结语义。v2 继续使用相同的工位镜像、十二日时钟和两个交付形式。正式签发名册在 R2/R7 当轮可读，站点决议有授权、作用域、生效区间和撤回日；设备需求按最新修订去重，同日按公开优先顺序分配。日初可用工位取决于模型此前实际投递的附件与已退信件。R11 查历史应签、实发与当时占用，R12 交割剩余席位。试跑诊断和两版独立回放见[实测报告](../../docs/results/w4-release-20261128/)。

两版各轮满分相同。v2 将 50 分分配给新增的实际业务责任：R2/R3/R4/R6/R9/R10 的附页分别 3/8/5/7/5/9 分，R11 附页及追溯共 10 分，R12 容量交割 3 分。同一日其余业务组按原比例分配剩余分值。登记事实、真实寄件与基于前态的补救可分别得分。现场层独立参考脚本从公开材料另算金标，测试期内核对撤回、当日有效性、重复设备、候补、冻结附件、晚到签收和错误邮箱。

### 按实际履约复评

新运行的 v2 同时输出原合同 `grade.json` 和按业务结果计分的 `grade-outcomes-1.json`。对已解包的 v2 冻结交付执行 `python -m tasks.w4.outcome_score RUN`，可查看每项的分母、案件预期与实际值、多余回执、得分及满分。两份成绩各自标明口径，历史正式分沿用原合同。权重、正反例和下一版场景设计见[W4 评分校准](../../docs/results/w4-release-20261128/outcome-calibration.md)。


## 夜班预约与客户异议版（v3）

夜班首次冻结版使用 `--edition 3`，说明区修订使用 `--edition 3.1`。沿用十二轮、同一 Docker 工位、四个业务工具和固定实例 17217/A。R2/R7 当班签单次日归还；R3 原邮件和 R4 是否退信决定夜班可申请量。R8 班长须交一张可改输入的预约表；R9 撤单调拨，R11 分别判断十二笔历史异议并给获准客户真实投递，R12 办理部分验收、跨站调拨与回执交割。公开规程随工位提供，运行中的评分只在宿主执行。

| 评分责任 | 满分 | 冻结证据 |
|---|---:|---|
| 日间业务 | 40 | v2 实际履约口径等比折算，夜班 H 件单独核算 |
| 夜班预约及重算 | 30 | R8、R9、R12 各取一份实际交班表。每份 5 分核当天输入和分案结果，5 分实际改容量和需求后用隔离的 Calc 重算，同时核应变及不变案件 |
| 历史异议与实际补救 | 24 | 十二案逐列还原原授权、实发、早期回条、现授权和行动共 12 分；真实处置另 12 分，错误收件人、提前、多余及重复发件影响该项 |
| 终班交割 | 6 | 按每案真实封数、最后回执、截止日状态核对，早期错误仍可如实交班 |

运行 `python -m tasks.w4.pilot runs/w4/new --edition 3`；离线 `python -m tasks.w4.pilot RUN --replay`。复评需 Docker 及运行所用的 office 镜像；在另一平台复建相同 Dockerfile 后可用 `W4_CALC_IMAGE` 显式指定当地镜像。重算容器无网络、无宿主挂载，只接收工作簿副本。Calc 运行故障保留为技术异常，可恢复后重放原作答。早期版本仍使用各自的 manifest 和评分合同。

3.1 在公开规程中指定日间手册的字段区和可选的 `## 说明` 段。历史或通用条款可以在说明中引用，字段区缺失、重复或另列相冲突的明确时限仍判为无效。重算测试在参评者真实填写的有效数值上施加变更，日常交付另与真实业务金标核对。首次盲测、同一份交付的两种复评和格式反例见[夜班实测报告](../../docs/results/w4-night-20261128/)。

## 四站共享容量调度（v4）

正式场使用 `--edition 4`，字段及柜面澄清版使用 `--edition 4.1`。新运行的规程明确了全案清单与办后填表时点，查询以共享表头返回，并可只查当天变动。4.1 将原通知时点分值拆成日期及本案办结后才寄出两条，通知责任总分不变。

十二轮、十二案、四个站。工位复用 W1 的隔离 Docker、W4 的档案及四个原生工具。本版本用四次真正修改柜面状态的业务批次替换早期版本的发手册工作，简报仅需异常与待办。每个工位初始相同，后续处理取决于模型自身的动作。新模型运行和离线验收分别用：

```sh
python -m tasks.w4.pilot runs/w4/quota --edition 4.1
python -m tasks.w4.pilot runs/w4/quota --replay
python -m tasks.w4.tests.quota_controls
```

| 日 | 交互 / 环境变化 | 可冻结的证据 |
|---:|---|---|
| 1–2 | 接手台账、审查限时签发原件与跨站续办券 | 案号、原占位、保护底线、额度、批文与优先号 |
| 3–4 | 首批按站清算；柜面可能退回旧版本或只受理一部分；次日提取 | 申请行、前值、实际受理号、最新版本、两个不同日期的占位 |
| 5–7 | 临时接管通知与代办职责，预排未来两个生效日。签单次日归还 | 解释与维持邮箱、代办系列及末日、按早期实占计算的预兑量 |
| 8–10 | 交出可复用预约表后切回主线；局部撤文、容量迁移、解除保护、跨站兑入 | 真正执行的调度、可独立重算的目标与柜面实占、部分受理后续办 |
| 11–12 | 异步提取产生异议；追回必要差额并通知相应客户，终班交割 | 客户实际收到的承诺、真实受理号、历史截止占位与变更重算 |

**计分单位是一个案件的一个业务事实。** `grade.json` 的 `atoms` 给出稳定 ID、轮次、案件、字段、期望、实际、证据来源、满分和得分。例：`R10/J01/调度-兑入` 只核第十日 J01 由另一案第三日实际缺额产生的权益。站内每一案的批准依据、基础额度、兑入、最终优先号、应配、实占、回执以及柜面动作各有独立证据。字段错一个只扣该字段；实际又造成其他客户短配时，该客户自己的交付会留下新的失分证据。缺列只影响该列，重复案号只影响该案。客户通知按是否应发选适用断言，但给每个客户的最高分相同。主榜按各断言所得相加，显示至四位小数。计算表的增容、停办响应来自宿主在无网 Calc 容器中修改副本，同时检查另一组客户维持原结果。评分代码、原始批次与答案均在模型挂载之外。

## 历史保障合同与客户履约（v4.2）

十二轮和十二案沿用四站工位。第2日从限时借阅的签章表辨别八份合同的归属；第7日后按单号将划转、停兑与第3日真实柜面占位关联。合同接续取两项保障的较大值，独立合同可累加，签发日与实际停兑日分开处理。四个未受此类合同直接覆盖的客户仍参与所在站的分配。第8、12日交班可修复上班留下的工作簿或重建等价文件，Calc 在零容量、充足容量和只能满足第二顺位一部分的容量下重算。

| 责任 | 满分 | 单位及证据 |
|---|---:|---|
| 按时履约 | 72 | 4 个实际办理日 × 12 案，每个客户日 1.5 分。宿主以应配量对真实柜面终态；维持原配额时需有正确签报或可核实的办理证据。纸面填数无法挽回真实短配。 |
| 客户通知 | 10 | 逐案核该通知谁、何时实际寄达、承诺和实绩；按应发或应维持分支保持每案上限相同。 |
| 交班工作簿 | 8 | 按案核原输入、基线输出和 Calc 变更结果。检查受影响的案件与其他站的稳定性。 |
| 交付证据 | 8 | 逐字段核授权、预排、回查及结班记录。 |
| 操作范围 | 2 | 按案核实际办理权限，另核多余通知与无归属记录。 |

`grade.json` 为所有细项记录预期、观测、取证位置及得分。`fulfilment` 单列客户日正确数与四个截点全部正确的客户数，全程指标不重复加分。错过一个截点仍可在后续正确补办时获得各自的分数。

## 4.3 联席纪要与续签

用 `python -m tasks.w4.pilot runs/w4/bulletins --edition 4.3` 开始一场新会话。默认入口仍复现 4.2。两版使用同一 Docker 镜像、十二轮、业务工具和评分权重。4.3 在九个业务日发放四站联席纪要，每份均包括现场、接驳和培训三种业务。借阅登记簿记录册名，两站中途换册，按签发日识别旧件。第 9 和 11 日的续签仅给出引用流水与变更项，需从早期原件接续同一业务的额度。
